Consumer Use Case

Using AI

Employees using AI tools like ChatGPT, Microsoft Copilot, Gemini, AI coding assistants, SaaS copilots, or agentic browsers for daily work - drafting emails, writing code, summarising documents, and automating tasks.

Scenarios & what can go wrong
Data leakage via GenAI chat - employee pastes customer contracts, source code, or PII into ChatGPT / Gemini. Data may be processed outside the intended control boundary depending on service terms, tenant settings, and policy.
AI coding assistants (GitHub Copilot, Cursor, Kiro) - developers autocomplete code using tools that may send file context, prompts, secrets, credentials, or proprietary logic to an external LLM.
Copilot on Enterprise SaaS (M365, Salesforce, CRM, ITSM) - embedded AI copilots inherit the data the user can see: emails, files, CRM records, tickets, or reports. Misconfigured permissions can surface data the employee was never meant to access.
Agentic browser (autonomous AI tasks) - AI browser agents act on behalf of employees: filling forms, clicking buttons, submitting transactions. A malicious webpage can inject instructions that hijack the agent's next action.
Shadow AI - IT has no visibility into which AI tools staff are using or what data they are sending.
PDPA exposure - sharing customer PII with an external AI service can create consent, purpose limitation, retention, and audit evidence risk.
Opening question
"Can you show which AI tools employees used in the last 30 days, and whether customer data was involved?"
Builder Use Case

Building AI

The org is developing its own AI-powered applications - internal chatbots, LLM APIs, AI agents, or GenAI features embedded in customer-facing products.

What can go wrong
Prompt injection - attacker crafts malicious input that can manipulate the AI application's behaviour or bypass intended controls.
Data exposure via AI response - the LLM returns PII, account data, or internal system details it should never have accessed.
Agentic AI abuse - an autonomous AI agent is manipulated into taking unintended actions: transferring funds, modifying records, or calling privileged APIs.
Poisoned open-source model - a model downloaded from HuggingFace contains hidden backdoors or malicious scripts that execute in production.
Opening question
"Did your AI application go through AI-specific adversarial testing before it went live, or only functional QA?"

Imperva - Product Map

Three products, three protection layers. WAAP is the foundational platform protecting the web frontend. API Security protects the API infrastructure layer. AI Application Security protects the LLM behavior layer. For AI applications - all three work together.

Builder Foundation Platform
WAAP (Web Application & API Protection)

Imperva WAAP combines WAF, Bot Protection, DDoS Protection, and API Security options in a cloud-delivered service. Protects the web frontend of AI applications - the interface through which users interact with AI-powered products.

Key capabilities
Web Application Firewall (OWASP Top 10, virtual patching)
Advanced Bot Protection - stops scrapers, credential stuffing, fake AI agent traffic
DDoS Protection - volumetric and application-layer attacks on AI-facing web services
Rate limiting and layer-7 controls for all web traffic to AI applications
Why it matters for AI apps
AI chat interfaces are web apps - they inherit all traditional web vulnerabilities (XSS, CSRF, injection)
Bots increasingly target AI services for scraping, abuse, and automated prompt attacks
WAAP is the first line of defense before traffic even reaches the LLM layer
DCS entry point
Standalone / Cloud WAF replacement Existing Imperva Cloud WAF - WAAP upgrade
Builder

Dedicated API discovery and runtime protection layer. Helps find API endpoints, including undocumented or shadow APIs, and protects against OWASP API Top 10 threats. Validate protocol coverage such as REST, GraphQL, or gRPC in the customer's environment.

Key capabilities

OWASP API Top 10 protection (broken auth, excessive data exposure, mass assignment)

API activity evidence that can support audit and incident investigation

4
Objection handling
Traditional DLP may miss AI prompt risk when users describe sensitive information rather than paste exact patterns. Existing DLP is still valuable, but validate whether it can inspect prompt text, file uploads, code assistants, SaaS copilots, and the channels the customer actually uses.
Blocking alone often pushes users toward unmanaged alternatives. A stronger conversation is governed access: discover AI usage, allow approved tools, apply DLP/coaching, and log policy actions where the control path can see the traffic.
Security is easier to embed before go-live than after production usage starts. AI-specific testing should happen before launch because prompt injection, unsafe output, and data exposure issues are often architectural or policy-design problems.
Frame it as an expansion when the deployed control point is a real fit. NGFW and Prisma Access can lead to AI Access Security; Imperva WAAP can lead to AI Application Security; Forcepoint DLP/ONE can lead to AI data security. Validate scope before presenting effort or commercial path.
For current F5 AI conversations, position AI Guardrails and AI Red Team rather than legacy AI Gateway language. Use F5's SecureIQLab validation as supporting evidence, then validate the customer's deployment model.

Machine identity lifecycle, least-privilege, ownership, approval context, and evidence for high-risk agent actions
